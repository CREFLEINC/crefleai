# Feature Specification: 추론 워커 분리 및 복수 모델 동시 서비스

**Feature Branch**: `feat/multi-model-workers`

**Created**: 2026-11-09

**Status**: Draft

**Input**: User description: "이슈 CREFLEINC/crefleai#49. 추론 워커 모듈을 만들어 물리적으로 분리된 서버에서 실행하거나 동일 PC의 다른 GPU를 할당받아 별도 프로세스로 동작시키고, gateway에서 지정된 모델 또는 인스턴스 id 식별자로 연결해 여러 개의 모델을 동시 서비스할 수 있도록 플랫폼을 확장한다."

## 배경

현재 CrefleAI는 게이트웨이가 같은 컨테이너 안에서 추론 워커를 하나만 직접 띄워 한 번에 모델 1개만
서비스한다. 다른 모델을 쓰려면 관리자가 기존 모델을 내리고 교체해야 하며, 그동안 서비스가 끊긴다.
GPU 전체가 하나의 컨테이너에 묶여 있어 GPU별·서버별로 모델을 나눠 올릴 수도 없다.

이 기능은 추론 워커를 독립 실행 단위로 분리하고, 게이트웨이가 요청마다 알맞은 워커를 찾아 전달하게 해
여러 모델을 동시에 서비스하도록 한다. 2026-08-10 분산 추론 Gateway 구축 계획의 1단계(Worker 분리)와
2단계(분산 라우팅)에 해당한다.

## Clarifications

### Session 2026-11-09

- Q: 워커 등록과 모델 배치를 어떻게 관리하는가? → A: 운영자가 워커를 직접 기동하고, 관리자 화면에서
  등록·해제한다. 게이트웨이 재시작은 필요 없다. 원격 워커의 모델 다운로드·기동 제어는 범위 밖이다.
- Q: 기존 단일 컨테이너 방식(게이트웨이가 로컬 워커를 직접 기동하고 관리자 화면에서 모델 교체)을 유지하는가?
  → A: 호환 모드로 유지한다. 로컬 워커도 등록된 워커 인스턴스 하나로 취급한다.
- Q: 인스턴스 식별자 지정은 누구에게 허용하는가? → A: 관리자·운영 점검용으로만 허용한다. 외부 API
  사용자는 모델 식별자로만 호출한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 여러 모델을 같은 주소로 동시에 호출 (Priority: P1)

API 사용자는 기존과 같은 API 주소와 토큰으로 요청하되, 요청의 모델 값만 바꿔 서로 다른 모델을
호출한다. 두 모델은 서로를 기다리지 않고 동시에 응답한다.

**Why this priority**: 이 기능의 핵심 가치다. 이것만 구현돼도 모델 교체 없이 용도별 모델을 함께
쓸 수 있다.

**Independent Test**: 서로 다른 모델을 서비스하는 워커 2개를 게이트웨이에 연결한 뒤, 같은 토큰으로
두 모델에 일반 요청과 스트리밍 요청을 동시에 보내 각각 올바른 모델이 응답하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 모델 A와 모델 B를 서비스하는 워커가 각각 준비됨, **When** 사용자가 모델 A를 지정해
   요청함, **Then** 모델 A를 서비스하는 워커가 응답하고 응답의 모델 값이 A이다.
2. **Given** 같은 상태, **When** 사용자가 모델 A와 모델 B에 스트리밍 요청을 동시에 보냄,
   **Then** 두 응답이 동시에 진행되고 각 스트림은 끝 표시까지 손실·변형 없이 전달된다.
3. **Given** 같은 상태, **When** 사용자가 서비스 모델 목록을 조회함, **Then** 모델 A와 모델 B가
   모두 목록에 나오고 각 모델의 컨텍스트 길이가 함께 표시된다.
4. **Given** 기존 단일 모델용으로 작성된 클라이언트 코드, **When** 주소·토큰 변경 없이 모델 값만
   지정해 호출함, **Then** 코드 수정 없이 동작한다.

### User Story 2 - GPU·서버를 나눠 워커 운영 (Priority: P1)

운영자는 같은 GPU 서버에서 GPU별로 서로 다른 모델 워커를 띄우거나, 다른 GPU 서버에서 워커를
실행해 게이트웨이에 연결한다. 각 워커는 독립적으로 기동·중지·재시작된다.

**Why this priority**: 워커를 독립 실행할 수 없으면 User Story 1이 성립하지 않는다. User Story 1과
함께 최소 기능 단위를 이룬다.

**Independent Test**: 게이트웨이 없이 워커 하나를 특정 GPU에 할당해 단독 실행하고 상태 확인과
추론이 되는지 확인한다. 이어서 같은 PC에서 다른 GPU에 두 번째 워커를 띄워 두 워커가 서로 다른 GPU를
쓰는지 확인한다.

**Acceptance Scenarios**:

1. **Given** GPU가 2개인 서버, **When** 운영자가 GPU 0번과 1번에 각각 다른 모델 워커를 실행함,
   **Then** 두 워커는 지정된 GPU만 사용하고 서로 간섭하지 않는다.
2. **Given** 게이트웨이와 다른 서버에서 실행 중인 워커, **When** 운영자가 그 워커를 게이트웨이에
   연결함, **Then** 해당 워커의 모델이 서비스 모델 목록에 나타나고 호출할 수 있다.
3. **Given** 서비스 중인 워커 2개, **When** 운영자가 그중 하나를 중지·재시작함, **Then** 다른 워커의
   서비스는 중단 없이 계속된다.

---

### User Story 3 - 같은 모델의 복수 인스턴스 운영과 인스턴스 점검 (Priority: P2)

운영자는 같은 모델을 여러 워커 인스턴스로 띄울 수 있다. 외부 API 사용자는 모델 식별자로만 호출하고,
게이트웨이가 그 모델을 서비스하는 준비된 인스턴스 중 하나로 요청을 보낸다. 관리자는 관리자 기능에서
인스턴스 식별자를 지정해 특정 인스턴스를 직접 점검 호출할 수 있다.

**Why this priority**: 같은 모델의 복제본 운영과 특정 GPU·서버 대상 점검에 필요하지만, 모델이
하나씩만 떠 있는 초기 운영에서는 없어도 User Story 1·2가 가치를 준다.

**Independent Test**: 같은 모델의 워커 인스턴스 2개를 연결한 뒤, 외부 API 요청이 준비된 인스턴스로
나뉘어 가는지, 관리자 점검 호출이 지정한 인스턴스로만 가는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 같은 모델의 인스턴스 X와 Y가 준비됨, **When** 사용자가 모델만 지정해 여러 번 요청함,
   **Then** 요청이 X와 Y로 나뉘어 처리된다.
2. **Given** 같은 상태에서 인스턴스 X가 준비되지 않음, **When** 사용자가 모델만 지정해 요청함,
   **Then** 인스턴스 Y가 응답한다.
3. **Given** 인스턴스 X와 Y가 준비됨, **When** 관리자가 관리자 기능에서 인스턴스 X를 지정해 점검 호출함,
   **Then** 인스턴스 X가 응답한다.
4. **Given** 인스턴스 X가 준비되지 않음, **When** 관리자가 인스턴스 X를 지정해 점검 호출함,
   **Then** 다른 인스턴스로 바꾸지 않고 "준비되지 않음" 오류를 반환한다.
5. **Given** 외부 API 사용자, **When** 요청에 인스턴스 식별자를 넣어 보냄, **Then** 인스턴스 식별자는
   라우팅에 쓰이지 않고 모델 식별자 기준으로만 처리된다.

---

### User Story 4 - 워커 연결·상태 관리 (Priority: P2)

운영자는 워커를 직접 기동한 뒤, 관리자 화면에서 워커의 주소를 입력해 등록하고 필요 없어지면 해제한다.
등록·해제에 게이트웨이 재시작은 필요 없다. 관리자는 연결된 워커 목록과 각 워커의 모델, 할당 GPU·서버,
준비 상태, 최근 오류를 확인한다.

**Why this priority**: 여러 워커를 운영하려면 상태를 한 곳에서 봐야 하지만, 최소 기능은 User Story 1·2로
먼저 성립한다.

**Independent Test**: 관리자 화면에서 워커 2개를 등록한 뒤 하나를 중지하고, 해당 워커가 "준비되지 않음"으로
일정 시간 안에 표시되는지 확인한다. 이어서 그 워커를 해제해 목록과 서비스 모델 목록에서 사라지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 운영자가 워커를 기동함, **When** 관리자가 관리자 화면에서 그 워커의 주소를 등록함,
   **Then** 게이트웨이 재시작 없이 워커의 모델이 서비스 모델 목록에 나타난다.
2. **Given** 등록된 워커, **When** 관리자가 그 워커를 해제함, **Then** 새 요청은 그 워커로 가지 않고,
   처리 중이던 요청은 끝까지 처리된다.
3. **Given** 워커 2개가 연결됨, **When** 관리자가 워커 목록을 조회함, **Then** 각 워커의 식별자, 모델,
   위치(서버·GPU), 준비 상태가 표시된다.
4. **Given** 준비된 워커가 중지됨, **When** 일정 시간이 지남, **Then** 해당 워커는 "준비되지 않음"으로
   표시되고 라우팅 대상에서 빠진다.
5. **Given** 중지됐던 워커가 다시 준비됨, **When** 일정 시간이 지남, **Then** 자동으로 라우팅 대상에
   다시 포함된다.

---

### User Story 5 - 기존 단일 서버 운영에서 전환 (Priority: P3)

운영자는 현재 doctordoom의 단일 컨테이너 운영에서 새 구조로 전환한다. 전환 절차가 문서화되어 있고,
전환 중에도 기존 토큰·관리자 계정·다운로드된 모델 파일을 그대로 쓴다.

**Why this priority**: 실서비스 반영에 필요하지만, 기능 개발·검증은 전환 없이도 진행할 수 있다.

**Independent Test**: 기존 데이터(토큰·관리자·모델 파일)가 있는 환경에서 전환 절차를 따라 새 구조를
띄운 뒤, 기존 토큰으로 기존 모델을 호출해 동작을 확인한다.

**Acceptance Scenarios**:

1. **Given** 기존 단일 컨테이너 운영 데이터, **When** 문서화된 전환 절차를 수행함, **Then** 기존 토큰과
   관리자 계정이 그대로 동작하고 모델 파일을 다시 받지 않아도 된다.
2. **Given** 전환 후 문제가 발생함, **When** 문서화된 롤백 절차를 수행함, **Then** 기존 단일 컨테이너
   운영으로 돌아간다.

---

### Edge Cases

- 요청한 모델을 서비스하는 워커가 하나도 없으면, 기존과 같은 OpenAI 형식의 "모델 없음" 오류를 반환한다.
- 모델은 등록돼 있지만 모든 인스턴스가 준비되지 않았으면 "서비스 불가" 오류를 반환한다.
- 요청에 모델 값이 없으면: 서비스 모델이 하나뿐일 때는 그 모델로 처리하고(기존 동작 유지), 둘 이상이면
  모델 지정이 필요하다는 오류를 반환한다.
- 다른 모델로 묵시적 대체(fallback)는 하지 않는다.
- 워커 연결이 응답 시작 전에 실패하면 같은 모델의 다른 준비된 인스턴스로 최대 1회 재시도하고,
  그래도 실패하면 오류를 반환한다.
- 스트리밍 응답 도중 워커가 끊기면 재시도하지 않고 오류 이벤트로 스트림을 끝낸다.
- 사용자가 요청 도중 연결을 끊으면 해당 워커의 추론도 중단되어 GPU 자원을 반환한다.
- 한 워커가 과부하로 대기열이 넘치면, 다른 모델 요청은 영향받지 않고 해당 모델 요청만 대기하거나
  "과부하" 오류를 받는다.
- 같은 인스턴스 식별자로 워커 두 개가 등록되려 하면 두 번째 등록을 거부한다.
- 워커와 게이트웨이의 버전이 달라 요청 형식이 맞지 않으면, 연결 단계에서 호환되지 않음을 표시하고
  라우팅 대상에서 제외한다.
- 게이트웨이 재시작 후에도 워커 등록 정보는 유지되고, 각 워커의 준비 상태는 다시 확인한다.

## Requirements *(mandatory)*

### Functional Requirements

**워커 독립 실행**

- **FR-001**: 추론 워커는 게이트웨이와 독립된 실행 단위로 기동·중지·재시작할 수 있어야 한다.
- **FR-002**: 워커는 기동 시 사용할 GPU를 지정할 수 있어야 하며, 지정된 GPU만 사용해야 한다.
- **FR-003**: 같은 PC에서 서로 다른 GPU를 할당한 워커 여러 개를 동시에 실행할 수 있어야 한다.
- **FR-004**: 워커는 게이트웨이와 다른 서버에서 실행되어 네트워크로 연결될 수 있어야 한다.
- **FR-005**: 워커는 생존 여부와 요청 수락 가능 여부(모델 로드 완료)를 구분해 알려야 한다.
- **FR-006**: 워커 인스턴스는 고유한 인스턴스 식별자와 서비스 모델 식별자를 가져야 한다.

**게이트웨이 라우팅**

- **FR-007**: 게이트웨이는 요청의 모델 식별자로 해당 모델을 서비스하는 준비된 워커를 찾아 요청을
  전달해야 한다.
- **FR-008**: 외부 API는 모델 식별자로만 라우팅한다. 인스턴스 식별자 지정은 관리자 점검 기능에서만
  허용하며, 지정된 인스턴스로만 전달해야 한다(대체 금지).
- **FR-009**: 일반 응답과 스트리밍 응답 모두 지원해야 하며, 스트리밍 내용은 변형 없이 전달해야 한다.
- **FR-010**: 서로 다른 모델에 대한 요청은 서로 기다리지 않고 동시에 처리되어야 한다.
- **FR-011**: 같은 모델의 준비된 인스턴스가 여러 개면 그중 하나로 요청을 분배해야 한다.
- **FR-012**: 게이트웨이는 다른 모델로 묵시적 대체를 하지 않아야 한다.
- **FR-013**: 응답 시작 전 연결 실패는 같은 모델의 다른 인스턴스로 최대 1회 재시도하고, 응답 시작 후
  중단은 재시도 없이 오류로 끝내야 한다.
- **FR-014**: 사용자가 연결을 끊으면 게이트웨이는 워커에 중단을 전파해야 한다.
- **FR-015**: 워커별 최대 동시 처리 수를 설정할 수 있어야 하며, 초과 요청은 정해진 시간만큼 대기한 뒤
  OpenAI 형식의 과부하 오류를 반환해야 한다.

**외부 API 호환**

- **FR-016**: 서비스 모델 목록 조회는 준비된 모든 모델을 각 모델의 유효 컨텍스트 길이와 함께 반환해야 한다.
- **FR-017**: 기존 API 주소·인증 토큰·요청·응답·오류 형식은 바뀌지 않아야 한다.
- **FR-018**: 모델 없음, 모델 미지정(서비스 모델 2개 이상), 인스턴스 준비 안 됨, 워커 연결 실패, 과부하는
  각각 구분되는 OpenAI 형식 오류로 반환해야 한다.

**워커 등록·상태 관리**

- **FR-019**: 게이트웨이는 연결된 워커의 식별자, 모델, 위치(서버·GPU), 준비 상태, 최근 오류를 관리해야 한다.
- **FR-020**: 게이트웨이는 워커 준비 상태를 주기적으로 확인해, 준비되지 않은 워커를 라우팅 대상에서
  빼고 다시 준비되면 자동으로 포함해야 한다.
- **FR-021**: 관리자는 관리자 화면에서 워커를 등록(주소 입력)·해제하고, 워커 목록과 상태를 확인할 수
  있어야 한다. 등록·해제는 게이트웨이 재시작 없이 반영되어야 한다.
- **FR-021a**: 워커 해제 시 새 요청은 그 워커로 보내지 않고, 처리 중인 요청은 끝까지 처리해야 한다.
- **FR-021b**: 원격 워커의 모델 다운로드·기동·중지는 게이트웨이가 제어하지 않는다. 운영자가 워커 서버에서
  직접 수행한다.
- **FR-022**: 워커 등록 정보는 게이트웨이 재시작 후에도 유지되어야 한다.
- **FR-023**: 중복 인스턴스 식별자 등록은 거부해야 한다.

**보안**

- **FR-024**: 워커는 게이트웨이 전용 내부 자격 증명이 있는 요청만 처리해야 한다. 내부 자격 증명은
  사용자 API 토큰과 분리하고, 저장소·이미지·로그에 넣지 않는다.
- **FR-025**: 워커는 외부 사용자에게 직접 노출되지 않아야 하며, 배포 문서에 접근 제한 방법을 명시해야 한다.
- **FR-026**: 게이트웨이와 워커 사이 로그에는 프롬프트·생성 본문을 남기지 않고 요청 식별자, 모델, 인스턴스,
  지연 시간, 결과만 남긴다.

**관측·운영**

- **FR-027**: 관리자 모니터링은 모델·인스턴스별 요청 수, 성공·실패, 처리 중 요청 수를 보여야 한다.
- **FR-028**: 기존 단일 컨테이너 운영에서 새 구조로의 전환·롤백 절차를 배포 문서에 포함해야 한다.
- **FR-029**: 전환 시 기존 사용자 토큰, 관리자 계정, 다운로드된 모델 파일을 그대로 사용할 수 있어야 한다.
- **FR-030**: 기존 방식(게이트웨이가 로컬 워커를 직접 기동하고 관리자 화면에서 모델 다운로드·교체)을
  호환 모드로 유지해야 한다. 호환 모드의 로컬 워커는 등록된 워커 인스턴스 하나로 취급되어, 원격 워커와
  함께 라우팅·상태 표시·모니터링 대상이 된다.

### Key Entities

- **워커 인스턴스**: 모델 하나를 로드해 추론을 수행하는 독립 실행 단위. 인스턴스 식별자, 서비스 모델,
  위치(서버 주소·GPU), 최대 동시 처리 수, 준비 상태, 최근 오류, 마지막 상태 확인 시각을 가진다.
- **서비스 모델**: 외부 사용자가 요청에 지정하는 모델 식별자. 하나 이상의 워커 인스턴스에 연결되며,
  카탈로그 모델 정보(이름, 컨텍스트 길이, 라이선스)를 참조한다.
- **라우팅 결정**: 요청 하나에 대해 선택된 인스턴스와 그 이유(모델 일치·인스턴스 지정·재시도)를 기록한
  운영용 정보. 요청 식별자로 추적한다.
- **내부 자격 증명**: 게이트웨이가 워커에 요청할 때 쓰는 비밀값. 사용자 토큰과 별개로 관리한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 서로 다른 모델 2개 이상을 동시에 서비스하고, 두 모델에 동시 요청 시 각 요청의 첫 응답까지
  걸리는 시간이 각 모델을 단독으로 호출할 때보다 20% 이상 늘지 않는다.
- **SC-002**: 같은 PC에서 GPU별로 워커 2개 이상, 별도 서버에서 워커 1개 이상을 연결해 운영할 수 있다.
- **SC-003**: 한 워커를 중지해도 다른 모델의 요청 성공률이 99% 이상 유지된다.
- **SC-004**: 중지된 워커는 30초 이내에 라우팅 대상에서 빠지고, 다시 준비되면 30초 이내에 복귀한다.
- **SC-005**: 기존 단일 모델용 클라이언트가 코드 수정 없이(모델 값 지정만으로) 100% 동작한다.
- **SC-006**: 신규 워커 하나를 추가해 서비스 목록에 노출하기까지 운영자 작업이 문서 절차 기준 15분 이내다
  (모델 파일 준비 시간 제외).
- **SC-007**: 전환 후 기존 사용자 토큰을 하나도 재발급하지 않는다.

## Assumptions

- 워커 인스턴스 하나는 모델 하나만 로드한다. 한 GPU에 여러 모델을 올리려면 워커를 여러 개 띄운다.
- 게이트웨이는 1개 인스턴스로 운영한다. 게이트웨이 이중화와 공유 저장소 전환은 범위 밖이다.
- 워커와 게이트웨이는 사내 사설망으로 연결되며, 공용 인터넷 노출은 고려하지 않는다.
- 같은 모델 인스턴스 간 분배는 단순 방식(준비된 인스턴스 순환 또는 처리 중 요청이 적은 쪽)으로 충분하다.
  요청 내용 기반 자동 모델 선택은 범위 밖이다.
- 지원 API는 기존과 같이 모델 목록 조회와 채팅 완성이다. 임베딩 등 다른 API는 범위 밖이다.
- 원격 워커가 쓸 모델 파일은 운영자가 해당 서버에 미리 준비한다. 원격 다운로드·배포 자동화(제어 계층)는
  범위 밖이며, 관리자 화면의 모델 다운로드는 호환 모드의 로컬 워커에만 적용된다.
- 기존 모델 카탈로그를 서비스 모델 정보의 기준으로 계속 사용한다.
