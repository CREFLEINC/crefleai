# Research: 추론 워커 분리 및 복수 모델 동시 서비스

**작성일**: 2026-11-09 | **명세**: [spec.md](spec.md) | **계획**: [plan.md](plan.md)

현재 코드(`server/src/crefleai/`)와 헌법(`.specify/memory/constitution.md`)을 기준으로 계획 단계의 미지수를
결정한다. 각 항목은 결정 · 근거 · 검토한 대안 순서로 적는다.

---

## R1. 워커 패키징과 실행 단위

- **결정**: 워커를 별도 저장소·패키지로 떼지 않고 기존 `crefleai` 패키지 안에 두고, 새 실행 명령
  `crefleai-worker`를 추가한다. 원격 워커는 게이트웨이와 **같은 Docker 이미지**를 다른 명령으로 실행한다
  (`command: crefleai-worker ...`). 호환 모드의 로컬 워커는 지금처럼 게이트웨이가 서브프로세스로 띄우되,
  같은 워커 코드(`crefleai.worker`)를 쓴다.
- **근거**: 추론 코드(`worker/app.py`), 카탈로그, 사양 판정 로직을 게이트웨이와 워커가 공유해야 한다.
  이미지 하나로 빌드·태그·배포 절차(`crefleai-deploy-orchestrator`)를 그대로 쓸 수 있고, 게이트웨이·워커
  버전이 항상 같은 태그로 맞춰진다.
- **대안**: (a) 워커 전용 경량 이미지 — 빌드 파이프라인이 둘이 되고 CUDA 빌드 시간이 두 배. 후속 최적화로 미룸.
  (b) llama.cpp `llama-server` 바이너리를 워커로 사용 — 자가 등록·사양 판정·인증을 별도 사이드카로 구현해야
  하고, 기존 Harmony·오류 형식 처리와 달라져 회귀 위험이 큼.

## R2. GPU 할당

- **결정**: 워커는 `--gpus 0,1`처럼 GPU 번호를 받는다. 워커 프로세스는 `llama_cpp`를 import하기 **전에**
  `CUDA_DEVICE_ORDER=PCI_BUS_ID`, `CUDA_VISIBLE_DEVICES=<지정값>`을 설정한다. Docker로 실행할 때는 compose의
  `device_ids`로 컨테이너에 해당 GPU만 넘기고 `--gpus`는 생략(컨테이너 안의 전체 = 할당분)한다. 여러 GPU를
  지정하면 llama.cpp 기본 분할(레이어 단위)을 그대로 쓴다.
- **근거**: CUDA 기본 장치 순서(가장 빠른 GPU 우선)와 NVML 순서(PCI 버스)가 다를 수 있어, 사양 판정(NVML)과 실제
  할당(CUDA)이 다른 GPU를 가리키는 사고를 막으려면 PCI 순서로 통일해야 한다. `CUDA_VISIBLE_DEVICES`는 import
  후에는 효과가 없다.
- **대안**: `Llama(main_gpu=..., tensor_split=...)`만 사용 — 다른 GPU에도 CUDA 컨텍스트가 생겨 메모리를 점유하므로
  "지정된 GPU만 사용"(FR-002)을 보장하지 못함.

## R3. 워커 자가 등록 프로토콜

- **결정**: GitHub Actions runner와 같은 2단계 자격 증명 구조를 쓴다.
  1. **등록 토큰**: 관리자가 발급. 32바이트 난수(`crefle_reg_` 접두어)이며 DB에는 SHA-256 해시만 저장한다.
     기본 1시간 유효, 유효 기간 안에서 재사용 가능, 폐기 가능. 발급 시 한 번만 화면에 보여준다.
  2. **워커 키**: 등록 성공 시 발급. `HMAC-SHA256(CREFLEAI_JWT_SECRET, "crefleai-worker:" + credential_id)`로
     **파생**하므로 DB에는 `credential_id`만 저장한다. 워커는 키를 상태 파일(`<state-dir>/credentials.json`,
     권한 600)에 저장하고, 재시작 시 이 키로 재연결한다. 같은 키를 **양방향**에 쓴다 — 워커→게이트웨이(재연결)와
     게이트웨이→워커(추론·상태 확인) 모두 `Authorization: Bearer <워커 키>`.
  3. **주소 검증**: 워커는 등록 요청에 일회용 `nonce`를 넣고, 게이트웨이는 워커가 알린 `advertise_url`로
     `GET /internal/status`를 호출해 같은 `nonce`가 돌아오는지 확인한 뒤에만 등록을 완료한다(FR-021c).
  4. **재연결**: 워커 시작 시 상태 파일이 있으면 `POST /api/workers/connect`, 없으면 등록 토큰으로
     `POST /api/workers/register`. 재연결 시 주소·GPU·컨텍스트가 바뀌었으면 갱신한다. 모델이 바뀌면 같은
     인스턴스의 모델을 갱신한다(명세 엣지 케이스).
  5. **제거**: 관리자가 워커를 제거하면 DB 행을 지워 `credential_id`가 무효가 되고, 파생 키는 더 이상 검증되지
     않는다. 제거된 워커의 재연결은 401 `worker_removed`로 거부되며 워커는 "새 등록 토큰 필요"를 표시하고
     종료한다.
- **근거**: 키를 파생하면 게이트웨이가 평문 비밀을 저장하지 않으면서도 워커에게 요청을 보낼 때 같은 키를
  다시 계산할 수 있다. 등록 토큰은 짧게, 워커 키는 길게 쓰는 구조가 runner 모델과 같아 운영자가 이해하기 쉽다.
- **대안**: (a) 워커 키를 DB에 평문 저장 — DB 백업 유출 시 모든 워커 사칭 가능. (b) mTLS — 사설망 단계에서는
  인증서 발급·갱신 부담이 큼(분산 Gateway 계획의 후속 단계). (c) 워커가 연결을 유지하는 역방향 터널 — 명세
  명확화에서 "게이트웨이 → 워커" 방향으로 결정됨.
- **영향**: `CREFLEAI_JWT_SECRET`을 바꾸면 모든 워커 키가 무효가 된다. 배포 문서에 명시하고, 교체 시 워커 재등록
  절차를 안내한다.

## R4. 워커 상태 확인

- **결정**: 게이트웨이가 등록된 모든 워커를 **5초마다** `GET /internal/status`로 확인한다(요청 타임아웃 3초).
  연속 3회 실패하면 `offline`, 응답이 오지만 `ready=false`면 `not_ready`, 정상이면 `ready`. `offline` 워커는
  계속 5초마다 확인해 복귀를 감지한다. 게이트웨이 재시작 시 DB의 워커 목록으로 즉시 1회 확인을 돌린다.
- **근거**: 최악의 경우 장애 감지 15초 + 확인 주기 5초 = 20초로 SC-004(30초)를 만족한다. 방향이 게이트웨이 →
  워커로 정해졌으므로 워커 쪽 하트비트는 두지 않는다.
- **대안**: 워커 → 게이트웨이 하트비트 — 게이트웨이가 워커 주소로 실제로 접근 가능한지는 따로 확인해야 하므로
  이중 구조가 됨.

## R5. 라우터와 대기열 (명세 NFR-001~006)

- **결정**: 모델마다 `ModelPool` 하나를 둔다. 게이트웨이는 단일 프로세스·단일 이벤트 루프이므로 풀 상태는
  asyncio 안에서만 바꾸고 별도 락을 두지 않는다.
  - **슬롯**: 인스턴스마다 `capacity`(= `max_concurrency`)와 `in_flight`를 게이트웨이가 센다. `in_flight ==
    capacity`면 "바쁨". 워커가 `/internal/status`로 알려주는 `in_flight`는 불일치 감지·로그용으로만 쓴다
    (게이트웨이가 워커의 유일한 호출자이므로 게이트웨이 카운터가 기준).
  - **획득(acquire)**: 대기열이 비어 있고 비어 있는 `ready` 인스턴스가 있으면 그중 `idle_since`가 가장 오래된
    인스턴스의 슬롯을 즉시 준다(NFR-001). 그렇지 않으면 `asyncio.Future`를 모델 대기열(`deque`) 뒤에 넣고
    기다린다(NFR-002). 대기열이 비어 있지 않으면 빈 인스턴스가 있어도 새 요청은 뒤에 선다(NFR-004 — 실제로는
    아래 직접 인계 때문에 이 상황이 생기지 않는다).
  - **반납(release) = 직접 인계**: 요청이 끝나 슬롯이 비면, 슬롯을 풀에 돌려놓지 않고 대기열 맨 앞의 살아 있는
    Future에 **그 슬롯을 바로 넘긴다**(NFR-003). 이렇게 하면 반납과 새 요청 도착 사이의 경합으로 새치기가 생길
    여지가 없다.
  - **Lease 객체**: 슬롯은 `Lease`로 표현하고 `release()`를 멱등으로 만든다. 일반 응답은 `try/finally`, 스트리밍은
    응답 제너레이터의 `finally`에서 반납한다. Starlette는 클라이언트가 끊으면 제너레이터를 닫으므로 `finally`가
    실행된다.
  - **비스트리밍 요청의 연결 끊김**: llama-cpp-python의 비스트리밍 호출은 중간에 멈출 수 없다. 사용자가 끊어도
    워커는 끝까지 계산하므로, 게이트웨이는 워커 호출이 실제로 끝날 때까지 슬롯을 잡아 둔다(shield된 태스크).
    그래야 "비어 있다"고 판단한 워커가 실제로 바쁜 상황이 생기지 않는다.
  - **스트리밍 요청의 연결 끊김**: 게이트웨이가 워커 스트림을 닫으면 워커의 기존 `stop` 이벤트가 토큰 사이에서
    생성을 멈춘다(`worker/app.py`의 기존 동작). 슬롯은 스트림을 닫은 직후 반납한다.
  - **대기 중 취소**: 대기 중인 사용자가 끊으면 Future가 취소되고, 인계 시 취소된 Future는 건너뛴다.
  - **상한**: 모델별 최대 대기 건수 `CREFLEAI_QUEUE_MAX_DEPTH`(기본 32), 최대 대기 시간
    `CREFLEAI_QUEUE_MAX_WAIT_SECONDS`(기본 300초). 넘으면 `503 server_overloaded`(아래 R6).
  - **인스턴스 변화**: 인스턴스가 `ready`가 되거나 새로 등록되면 빈 슬롯 수만큼 대기열 앞에서 인계한다.
    인스턴스가 `offline`/`not_ready`가 되면 새 인계 대상에서 빠지고, 그 모델에 `ready` 인스턴스가 하나도 남지
    않으면 대기 중인 요청 전부를 `503 model_not_ready`로 끝낸다.
  - **재시도와 순서**: 응답 시작 전 연결 실패(FR-013)는 그 인스턴스를 `not_ready`로 표시하고, 요청을 대기열
    **맨 앞**에 다시 넣어 순서를 지킨다. 재시도는 1회.
  - **관리자 점검 호출**: 인스턴스를 지정한 점검 호출은 모델 대기열 대신 인스턴스 전용 대기 목록에 들어가고,
    그 인스턴스의 슬롯이 비면 모델 대기열보다 먼저 인계받는다. 점검은 드물고 짧으므로 모델 대기열의 순서
    보장(NFR-003)은 일반 사용자 요청끼리의 순서로 정의한다.
- **근거**: 모델별 단일 FIFO + 직접 인계는 명세의 "요청한 순서대로, 먼저 끝난 워커로"를 그대로 구현하는 가장
  단순한 구조다. 게이트웨이를 1개 인스턴스로 운영한다는 가정(명세) 덕분에 분산 큐가 필요 없다.
- **대안**: (a) 워커별 대기열(Join-Shortest-Queue) — 먼저 끝난 워커가 다음 요청을 받는다는 요구를 어김.
  (b) `asyncio.Semaphore` — 대기 순서는 지키지만 어느 워커로 갈지와 결합되지 않고, 반납·도착 경합 시 새치기
  가능. (c) Redis 큐 — 게이트웨이 이중화 전에는 불필요.

## R6. 오류 계약

- **결정**: 기존 `{"error": {"message", "type", "code"}}` 형식을 유지하고, 명세 FR-018의 상황을 `code`로 구분한다.

  | 상황 | HTTP | type | code |
  |---|---|---|---|
  | 없는 모델 | 404 | `invalid_request_error` | `model_not_found` |
  | 모델 미지정 + 서비스 모델 2개 이상 | 400 | `invalid_request_error` | `model_required` |
  | 모델은 있지만 준비된 인스턴스 없음 | 503 | `server_error` | `model_not_ready` |
  | 대기열 가득 참·대기 시간 초과 | 503 | `server_error` | `server_overloaded` |
  | 워커 연결 실패(재시도 후) | 502 | `server_error` | `worker_unreachable` |

- **근거**: 현재 코드의 404·503·502 상태 코드를 그대로 두고 `code`만 채워 하위 호환을 지킨다(헌법 IV). 과부하에
  429 대신 503을 쓰는 이유는 사용자별 요율 제한이 아니라 서버 용량 문제이기 때문이다. openai SDK는 503을 기본
  2회 자동 재시도하며, 재시도 요청은 대기열 뒤에 다시 선다.
- **대안**: 429 `rate_limit_exceeded` — 사용자에게 "내가 너무 많이 보냈다"는 오해를 줌.

## R7. 모델 사양(최소·권장) 산정

- **결정**: 카탈로그 항목에 `spec` 필드를 추가한다.
  - `base_bytes`: 모델 가중치 + 연산 버퍼 + CUDA 컨텍스트 (컨텍스트 길이와 무관한 부분)
  - `kv_bytes_per_token`: 토큰 1개당 KV 캐시 크기 = `n_layer × (n_embd_k_gqa + n_embd_v_gqa) × 2바이트`
    (f16 KV, GGUF 메타데이터에서 계산)
  - `reference_ctx`: 측정 기준 컨텍스트 길이(기본 8192)
  - `source`: `measured` | `estimated`, `measured_on`: 측정 GPU·날짜
  - **최소 사양**(ctx) = `base_bytes + kv_bytes_per_token × ctx`
  - **권장 사양**(ctx, concurrency) = `base_bytes + kv_bytes_per_token × ctx × concurrency` × 1.2 (여유 20%)
- **측정 방법**: `server/scripts/measure_model_spec.py`를 doctordoom에서 실행한다. 모델을 `reference_ctx`로 로드한
  뒤 NVML 사용량 증가분을 재고, 기준 길이를 꽉 채운 프롬프트 1건을 처리한 뒤 최고 사용량을 다시 잰다.
  `kv_bytes_per_token`은 GGUF 메타데이터로 계산하고 측정값과 대조한다. 결과를 `catalog.json`에 기록한다(헌법 V
  "근사치는 실측으로 검증").
- **추정값**: 측정 전 모델은 `base_bytes = 파일 크기 × 1.10 + 1.0 GiB`(연산 버퍼·컨텍스트 여유)로 보수적으로 잡고
  `source=estimated`로 표시한다.
- **대안**: 실행 시점에 GGUF를 읽어 매번 계산 — 연산 버퍼 크기는 메타데이터만으로 정확히 알 수 없어 결국 실측이
  필요함.

## R8. 사양 판정 시점과 방법

- **결정**: 워커는 모델 로드 **전**에 NVML로 할당된 GPU의 `free` 메모리 합계를 읽어 최소 사양과 비교한다.
  미달이면 필요값·실제값을 출력하고 종료 코드 3으로 끝낸다(등록 안 함, 강제 옵션 없음 — FR-036). 최소 이상
  권장 미만이면 실행하고 등록 정보에 `spec_status=below_recommended`를 넣는다(FR-037). 로드에 실패하면 등록하지
  않고 종료 코드 4로 끝낸다(FR-039).
- **GPU 세대 확인**: 이미지 빌드 시 `CREFLEAI_CUDA_ARCHS`(현재 `120`)를 환경 변수로 넣고, 워커는 NVML의 compute
  capability가 이 목록에 없으면 실행하지 않는다(명세 엣지 케이스).
- **NVML 불가**: GPU 정보를 읽을 수 없으면 실행하지 않는다(명세 엣지 케이스). 테스트는 GPU 조회 함수를
  주입해 가짜 값으로 검증한다.
- **호환 모드**: 관리자 화면의 "서비스 시작"도 같은 판정 함수를 호출해, 미달이면 409 `insufficient_gpu_memory`로
  막는다(FR-038). 로컬 워커는 지금처럼 GPU 전체를 쓰므로 모든 GPU의 `free` 합계로 판정한다.
- **경합**: 같은 GPU에 워커 두 개를 동시에 띄우면 둘 다 판정을 통과한 뒤 메모리가 모자랄 수 있다. 운영 문서에
  "같은 GPU의 워커는 하나씩 기동"을 명시하고, 로드 실패는 FR-039 경로로 처리한다.

## R9. 동시 처리 수(`max_concurrency`)

- **결정**: 등록 프로토콜·라우터는 `max_concurrency`를 지원하지만, 이번 워커 엔진(llama-cpp-python 단일
  `Llama` 인스턴스)은 **1만 허용**한다. 워커에 1보다 큰 값을 주면 "이 워커 엔진은 동시 처리 1만 지원"을 출력하고
  종료한다.
- **근거**: llama-cpp-python의 `Llama` 객체는 동시 호출을 지원하지 않아 지금도 워커가 뮤텍스로 한 번에 하나만
  처리한다. 동시 처리를 늘리려면 `Llama` 인스턴스를 여러 개 띄워야 하는데, 이는 모델 가중치를 GPU에 여러 번 올리는
  것과 같아 같은 모델 워커를 여러 개 띄우는 것과 차이가 없다. 같은 효과는 워커 수로 얻는다.
- **영향**: 명세 FR-015의 "설정 가능(기본 1)"은 프로토콜·라우터 수준에서 충족하고, 엔진 제약은 문서에 명시한다.
  llama.cpp 서버의 병렬 슬롯을 쓰는 엔진으로 바꿀 때 값을 늘린다.

## R10. 등록 정보 저장

- **결정**: 기존 SQLite에 테이블 두 개를 추가한다 — `worker_registration_tokens`, `workers`. 상태(`ready` 등),
  `in_flight`, 최근 오류, 대기열은 게이트웨이 메모리에만 둔다. 마이그레이션은 기존처럼 `CREATE TABLE IF NOT
  EXISTS`로 처리한다.
- **근거**: 게이트웨이 1개 운영 가정. 재시작 후 유지가 필요한 것은 등록 정보뿐이다(FR-022).
- **대안**: PostgreSQL 전환 — 게이트웨이 이중화 단계의 과제.

## R11. 호환 모드(로컬 워커)

- **결정**: 기존 `WorkerManager`는 유지하고, 로컬 워커가 `running`이 되면 레지스트리에 인스턴스
  `local`(주소 `http://127.0.0.1:<worker_port>`, 내부 워커 키 사용)로 자동 등록한다. 정지·교체 시 해제한다.
  `CREFLEAI_LOCAL_WORKER`(기본 `true`)를 `false`로 두면 게이트웨이는 GPU 없이 라우팅만 한다.
- **근거**: 명세 Q2(호환 모드 유지)와 FR-030. 라우터는 로컬·원격을 구분하지 않으므로 코드 경로는 "누가 워커를
  띄우는가"에서만 갈린다.

## R12. 관측 지표

- **결정**: `RequestMetricsTracker`를 모델·인스턴스 라벨별로 확장하고, 모델별 대기 건수·최근 60초 대기 시간
  (평균·최대)·과부하 거절 수를 추가한다. 관리자 `GET /api/admin/metrics` 응답에 `models[]`, `workers[]`를 더한다
  (기존 필드는 유지). 로그에는 요청 ID·모델·인스턴스·대기 시간·처리 시간·결과만 남기고 본문은 남기지 않는다(FR-026).

## R13. 검증 방법

- **결정**:
  - 라우터·대기열: 실제 HTTP 없이 `ModelPool` 단위 테스트. 완료 시점을 `asyncio.Event`로 조종하는 가짜 워커로
    5명 동시 요청 시나리오(SC-011·012)를 결정적으로 검증한다.
  - 게이트웨이 API: 기존 `test_v1_api.py` 방식(가짜 워커 ASGI 앱 + `httpx.ASGITransport`)을 워커 2~3개로 확장.
  - 등록: 등록·재연결·제거·토큰 만료·주소 검증 실패를 API 테스트로.
  - 사양 판정: GPU 조회 함수 주입으로 미달·권장 미만·충족·NVML 불가·세대 불일치.
  - 실모델: `CREFLEAI_TEST_GGUF`로 워커 단독 실행 → 등록 → 추론 통합 테스트(`-m inference`).
  - 운영 검증: doctordoom에서 [quickstart.md](quickstart.md)의 시나리오(GPU별 워커 2개, 부하 시험).
