요약

CrefleAI는 공통 Gateway와 모델별 독립 추론 서버 구조로 전환한다. 새로운 Gateway 제품을 먼저 도입하지 않고, 현재 FastAPI 애플리케이션의 인증·OpenAI 호환 API·관리 기능을 유지하면서 로컬 단일 워커 결합을 네트워크 기반 ModelRegistry와 InferenceRouter로 교체한다.

결정. Gateway v1은 기존 Python·FastAPI 스택으로 구현한다. 모델 서버는 OpenAI 호환 내부 API를 제공하는 독립 컨테이너로 배포하며, 초기 라우팅 정보는 정적 설정으로 관리한다.

첫 번째 완료 지점은 기존 클라이언트 변경 없이 Gateway가 서로 다른 물리 서버의 두 모델 워커로 model 값에 따라 일반 응답과 SSE 스트리밍 요청을 전달하는 것이다. 원격 모델 다운로드와 프로세스 제어 자동화는 이 경로가 안정화된 뒤 별도 제어 계층으로 확장한다.

배경

현재 CrefleAI는 사내 GPU 서버에서 GGUF 모델을 제공하는 단일 서버형 서비스다. FastAPI 프로세스가 외부 API, JWT 인증, 관리자 화면, 모델 카탈로그를 제공하고, 같은 호스트의 추론 워커 서브프로세스를 직접 생성하고 감시한다.1

현재 구조의 제약

  • /v1/chat/completions가 하나의 WorkerManager 상태와 base_url에 직접 결합돼 있다.
  • WorkerManager는 127.0.0.1의 워커 한 개만 생성·감시한다.
  • Gateway와 워커가 하나의 컨테이너 이미지와 배포 주기를 공유하며, 컨테이너에 모든 GPU가 전달된다.
  • 토큰 allowlist와 설정이 로컬 SQLite에 있어 Gateway를 여러 인스턴스로 늘리면 상태 동기화가 되지 않는다.
  • 동시 서비스 모델 한 개와 요청 한 개씩 처리하는 정책으로 설계돼 있어 모델별 독립 확장과 임베딩 워크로드 수용이 어렵다.

활용할 자산. OpenAI 호환 API, JWT 토큰 관리, 관리자 UI, 모델 카탈로그, SSE 중계, 워커 헬스체크와 재시작 로직은 유지하거나 역할을 분리해 재사용한다.

목표와 범위

목표

  1. 사용자는 하나의 CrefleAI API 주소로 모든 허용 모델을 호출한다.
  2. 각 모델은 지정된 GPU 서버에서 독립적으로 배포·재시작·확장된다.
  3. Gateway는 요청의 모델과 기능을 검증하고 정상 endpoint로 전달한다.
  4. 모델별 장애와 과부하가 다른 모델 및 Gateway 관리 기능으로 전파되지 않는다.
  5. 추론 엔진을 바꿔도 외부 클라이언트 계약은 유지된다.

라우팅 원칙

  1. 외부 model ID는 실제 파일명과 분리한 안정적인 alias로 관리한다.
  2. 복수 모델 환경에서는 model을 필수로 하거나 명시적인 기본 alias만 허용한다.
  3. 같은 model ID의 준비된 복제본 사이에서만 부하를 분산한다.
  4. 다른 모델로의 fallback은 자동 적용하지 않으며, 별도 정책이 승인된 경우에만 노출한다.
  5. endpoint별 최대 동시성을 초과하면 제한된 대기 후 429 또는 503을 반환한다.
models:
  chat-general:
    capability: chat
    endpoints:
      - url: http://gpu-a.internal:8001
        max_concurrency: 2

  embedding-ko:
    capability: embeddings
    endpoints:
      - url: http://gpu-c.internal:8001
        max_concurrency: 16

클라이언트 연결 종료업스트림 요청 취소 전파불필요한 GPU 연산을 줄인다.

네트워크와 자격 증명

  • 외부에는 Gateway 또는 Edge Proxy만 노출한다.
  • Worker 포트는 사설망에서 Gateway 주소만 접근하도록 방화벽을 제한한다.
  • 초기에는 Worker 전용 내부 토큰을 사용하고 비밀값은 이미지와 저장소에 포함하지 않는다.
  • 보안 구역이 나뉘거나 다중 조직이 접근하면 Gateway와 Worker 사이에 mTLS를 적용한다.
  • 프롬프트와 생성 본문은 기본 로그에서 제외하고 request ID, 모델, 토큰 수, 지연만 기록한다.

실행 계획

단계별 실행 계획
단계핵심 작업산출물완료 기준
0. 계약 확정 모델 배치표, public model ID, 기능, 동시성, API 오류 계약 정의 아키텍처 결정 기록과 라우팅 설정 스키마 최소 두 모델과 담당 서버가 명시된다.
1. Worker 분리 Gateway와 Worker 이미지 분리, 원격 Worker 독립 실행, 내부 인증 GPU 서버별 Compose와 Worker health API Gateway 없이 각 Worker의 추론과 스트리밍을 검증한다.
2. 분산 라우팅 ModelRegistry, InferenceRouter, Chat·Embedding adapter 구현 모델별 라우팅과 통합 /v1/models 기존 클라이언트가 두 원격 모델을 선택 호출한다.
3. 신뢰성 readiness, 동시성 제한, timeout, circuit breaker, 취소 전파 오류 정책 테스트와 장애 시나리오 결과 한 Worker 장애가 다른 모델 요청에 영향을 주지 않는다.
4. 관측·부하 검증 Gateway·Worker·GPU 지표 연결, 스트리밍 부하 시험 대시보드와 모델별 기준 성능표 목표 부하에서 병목과 용량 계획 근거가 확인된다.
5. 운영 이중화 PostgreSQL 전환, Gateway 복제, Edge 부하 분산 Gateway 다중 인스턴스 배포와 복구 절차 Gateway 한 인스턴스 중단 중에도 신규 요청을 처리한다.
6. 제어 계층 원격 모델 다운로드, 배포, 버전 전환, Node Agent 또는 오케스트레이터 검토 분산 모델 운영 UI와 감사 기록 추론 데이터 경로와 독립적으로 모델 생명주기를 관리한다.

첫 번째 개발 마일스톤

기존 OpenAI 클라이언트를 변경하지 않고, CrefleAI Gateway가 서로 다른 물리 서버에서 실행되는 두 모델 Worker로 model 값에 따라 비스트리밍과 SSE 스트리밍 요청을 정확히 전달한다.

첫 마일스톤의 필수 검증 항목은 다음과 같다.

  • 정상 모델별 요청과 /v1/models 응답
  • 없는 모델, 기능 불일치, 준비되지 않은 모델의 오류 형식
  • SSE chunk와 [DONE]의 무변형 중계
  • Worker 연결 실패와 스트리밍 중단 처리
  • Gateway 종료 시 업스트림 연결 정리
  • Worker가 외부 네트워크에서 직접 접근되지 않음

재검토 조건

다음 조건이 발생하면 Gateway 또는 오케스트레이션 기술 선택을 다시 평가한다.

  • 동일 모델 복제본 수가 늘어 단순 round-robin으로 GPU 사용률과 대기열을 균형화하기 어려운 경우
  • 다중 노드 tensor·expert parallelism 또는 prefill/decode 분리가 필요한 경우
  • 노드 추가·교체가 빈번해 정적 endpoint 등록이 운영 병목이 되는 경우
  • 사용자·조직별 토큰 예산, 공급자별 비용, 외부 API fallback을 통합 관리해야 하는 경우
  • Gateway와 Worker의 수가 증가해 Compose 기반 배포·복구가 반복 작업의 주된 원인이 되는 경우

결론

CrefleAI의 분산 전환은 새 Gateway 제품 도입보다 현재 FastAPI Gateway와 로컬 Worker의 결합을 분리하는 것에서 시작한다. 먼저 Worker를 독립 컨테이너와 표준 내부 API로 만들고, 정적 ModelRegistry와 InferenceRouter로 두 원격 모델을 연결한다. 이후 장애 정책, 관측, PostgreSQL 기반 Gateway 이중화, 원격 모델 제어 계층의 순서로 확장한다.

이 접근은 기존 CrefleAI의 인증·관리·클라이언트 호환성을 보존하면서 모델별 장애 격리와 수평 확장의 기반을 제공한다. 첫 마일스톤 완료 전에는 고급 Kubernetes 추론 플랫폼이나 동적 제어 계층을 필수 의존성으로 추가하지 않는다.

다음 단계

  1. 실제 모델·서버·GPU·목표 동시성을 담은 모델 배치표를 확정한다.
  2. Gateway v1 API와 정적 모델 레지스트리 스키마를 설계 문서로 고정한다.
  3. 현재 이미지에서 Worker를 분리하고 첫 번째 원격 GPU 서버에 독립 배포한다.
  4. WorkerManager 직접 의존을 InferenceRouter 인터페이스로 교체한다.
  5. 두 개 원격 모델의 비스트리밍·SSE 수직 경로를 자동 테스트한다.
